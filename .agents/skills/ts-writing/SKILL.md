# TypeScriptを書くときのルールや推奨方針

コードとコメントの共通方針は[コード記述共通ルール](../../../apm_modules/halby24/agent-common-package/.apm/skills/code-writing/SKILL.md)に従う。公開APIのdocコメントはTypeDocの記法で書く。

## 基本原則

- 静的に保証できる制約は、可能な限り型で表現する。
- 外部入力は境界で`unknown`として受け、実行時に検証してから内部の型へ変換する。型注釈や型アサーションは実行時の検証にならない。
- 型で表せない振る舞いや境界条件はテストで検証する。テストは実行時の入力検証やエラー処理を代替しない。
- `try-catch`は回復やエラーの変換が必要な境界に置く。フォールバックは仕様として必要な場合に限り、理由を残す。

## ルール

- `any`は原則禁止。どうしても使用する場合は、必要な理由と影響範囲をADRコメントに書く。
- 型アサーション`as`を使用する場合は、型の絞り込みで表現できない理由と、主張する型が成立する根拠をADRコメントに書く。
- ローカル変数は型推論を優先する。
- オブジェクトリテラルの型適合性を確認しつつ推論を活かしたい場合は`satisfies`を優先する。外部データの実行時検証には使えない。
- 相互排他的な状態は、判別用プロパティを持つユニオン型などで表現する。
- 単位・ID・座標系など、取り違えが実害につながるプリミティブ値にのみブランド型を使う。
- 状態の変更は所有者が明確な内部実装に閉じ込め、公開インターフェイスは可能な限り読み取り専用にする。`readonly`は実行時の凍結や深い不変性を保証しない。

## TypeDoc コメントの書き方

- 公開APIには役割と利用条件を書く。内部の項目には、名前や型から読み取れない情報がある場合に書く。
- 最初の段落は短い要約とし、詳細とは空行で分ける。型の説明を繰り返さず、単位、値域、欠損の意味、状態変化を補う。
- タグは必要なものだけ使う。内部の設計理由は通常コメントに書き、`@remarks`には利用判断に必要な補足を載せる。
- 関連項目は`{@link Scene.tick}`や`{@link Scene.tick | フレーム更新}`で参照する。

### モジュールスコープ

パッケージの入口や、責務の境界を説明する必要があるモジュールに概要を書く。すべてのファイルへの定型文は不要。
TypeDocでファイル全体の説明にする場合は、`@packageDocumentation`を含むコメントを、インポートより前の最初のコメントとして配置する。

```ts
/**
 * シーン内のアバターとカメラの状態管理。
 *
 * @packageDocumentation
 */
```

### クラス・インターフェース・型

- 表す概念と、利用者に保証する性質を書く。呼び出し順序や後片付けの責任がある場合は明示する。
- インターフェースには実装者が守る条件も書く。メソッド間の整合性や失敗時の挙動は、シグネチャだけでは保証できない。
- ユニオン型は各状態の意味と違いを説明する。型引数の役割が自明でなければ`@typeParam`で補う。

### 関数・メソッド

- `@param`: 引数名に続けて、単位、値域、省略時の扱いなどを書く。型注釈があれば`{number}`などの型指定は重ねない。
- `@returns`: 戻り値の意味と、`null`・`undefined`を返す条件を書く。`Promise`の場合は、完了が何を意味するかも説明する。
- `@throws`: 例外の種類と発生条件を書く。非同期APIでは、同期的な例外と`Promise`の拒否を区別して説明する。
- `@remarks`: 入力オブジェクトの変更、呼び出し順序、失敗時に処理が途中まで進むかなど、必要な補足を書く。

以下はAPI宣言の例（実装は省略）。

```ts
/** フレーム単位の描画統計。 */
export interface FrameStat {
  /** 描画命令を発行したアバターの数。 */
  readonly avatarCount: number;
}

/**
 * ポーズを更新して描画命令を発行し、このフレームの統計を返す。
 *
 * @param deltaTime - 前回の更新からの経過時間（ミリ秒）。有限かつ0以上1000未満。
 * @returns 描画命令を発行したアバター数を含む統計。
 * @throws `RangeError` — `deltaTime`が範囲外、`NaN`、または無限大の場合。
 * @remarks
 * 入力が不正な場合、シーンの状態は変更せず、描画命令も発行しない。
 */
export declare function tick(deltaTime: number): FrameStat;
```

### プロパティ・既定値

値の意味や省略時の扱いを説明する。`@defaultValue`には既定値そのものと適用条件を書き、採用理由とは分ける。
インターフェースの省略可能なプロパティには初期化処理がないため、どの処理が既定値を補うかを明示する。

```ts
/** シーン生成時に適用する設定。 */
export interface SceneOptions {
  /**
   * シーン生成時にカメラを有効にするか。
   *
   * @defaultValue `false`（省略時にシーン生成処理が適用）。
   */
  readonly cameraActive?: boolean;
}
```

### 説明の共有

- 契約が共通なら、参照先を指定した`{@inheritDoc SceneUpdater.tick}`などで説明を共有する。
- コピーされるのは要約、`@remarks`、`@param`、`@typeParam`、`@returns`。`@throws`・`@example`・`@defaultValue`は必要に応じて明示する。
- 一部だけ共通する場合や、実装固有の補足が必要な場合は、`{@link ...}`で共通の説明を参照し、その項目の挙動を書く。

### 使用例と検証

- 利用手順が分かりにくいAPIには`@example`で短い使用例を書く。必要なインポートや非同期処理を示し、実装を省く宣言例とは区別する。
- 数値の範囲と単位、戻り値の型と説明、例外条件が実装と一致するか確認する。`number`の値域に制約がある場合は`NaN`・無限大の扱いも確認する。
- TypeDocの生成だけでは使用例の型や挙動は検証されない。使用例を変更した場合は型チェックし、振る舞いの保証は既存のテスト方針に従う。
- TypeDocの生成手順がある場合は、変更したタグやリンクの警告、生成結果を確認する。

タグの詳細は[TypeDocのタグ一覧](https://typedoc.org/documents/Tags.html)、説明の共有範囲は[inheritDocの仕様](https://typedoc.org/documents/Tags.__inheritDoc_.html)を参照する。

## 改修時の扱い

変更箇所と関連するコード・コメントはこの方針に揃える。型チェックやlintの設定を強化する場合は、現在の設定と診断結果を確認し、影響範囲を示して提案する。
