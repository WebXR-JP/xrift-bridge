# 文書の書き方

ここで記載しているルールはこのリポジトリのオリジナルのドキュメントに対して適用される
submoduleや外部から持ってきてパッチしているものなどには適用せず、元の書き方を尊重する

## 基本ルール

- 日本語で書く。
- 過去について書かない。今または将来のことだけ書く。
- 見出しに数値を付けない (`## 1.1 hoge` などはだめ)
- ライブラリ内蔵機能の名前など、スコープの小さい用語には語釈をつけるか分かりやすい言い回しに置き換えること
- このスキルの内容に明らかに従っていないドキュメントを編集するときは全体を直す

## ルールの書き方

ドキュメントのその内容がAIエージェントが守るべき内容として書かれる場合、以下のことに気をつけて

- **具体化しすぎない**
  - 目標そのものを書き、目標を達成するための具体的な手法について書きすぎない
- **同じことを何度も書かない**
  - 担当者が肯定文のみから意図を汲み取ってくれることを期待してよい
  - 特に肯定文と否定文が並ぶ構造において、否定文を消しても概ね目指している内容が変化しないならば書かないことを優先する
    - "〇〇であることを確認、××だけして完了としない"　という文は実質的に前半だけでよいことが多い

## 読みやすさのためのルール

- 口語を混ぜていい。文体を柔らかめにする。
- 論理構造を厳密に表現するよりも書かなくても伝わることを省くことを優先する
- 同じ意味を常に同じ単語で表現する必要はなく、だいたい伝わればOK
  - 例: SSoTと正本
- 単語選びでも柔らかさを優先する
  - 可読性→読みやすさ、過度な→〇〇しすぎ、簡潔に→短めに
- 複数の内容が実質的に同じことを言っている場合、なるべくまとめる

## 内容について

異なるドキュメント、ソースコード、スキルなどに同じ情報を書くと陳腐化しやすいので、SSoTと参照で構成する
どれを正本にするべきか判断しかねる場合はユーザーまたは上位エージェントに確認して

## 英単語の書き分けについて

- 固有名詞やライブラリの名前など、本来英単語であるものは英単語として書く
  - 例: WebGPU, Unity, Gradle, Android
- プログラミング、3DCG用語のうち、日本語名が浸透しているものは日本語で書く
  - 例: 構造体、関数、定数、透過、平行光源（ディレクショナルライト）
- 訳語が浸透していない用語は、基本的にカタカナが望ましい
  - 例: リフレクション、フレーム、テクスチャ、リソース、ストア
- 業界標準として定着している用語を無理に漢字へ和訳（造語化）しない
  - 和訳しすぎは認知負荷を上げ、古風な印象や誤解を生む。
  - 例: `Resource` を「資源」ではなく「リソース」、`Directional Light` は「ディレクショナルライト」、`Store` を「保管庫」ではなく「ストア」とする。
  - ドメイン固有の概念として独自の和訳（例: `Instance` をアバターの「個体」など）をあてる場合は、初出時や必要に応じて「アバター個体（インスタンス）」のように補足して認知の齟齬を防ぐ。
- ただし、ツール名として一体化している名前の一部分だけ翻訳するのはおかしい
  - `Metal Frame Debugger`をMetalフレームデバッガと書くべきではない
- エラーメッセージなど外部から与えられる文の内容に関しては無理に翻訳しない
  - `NullReferenceException`という例外が発生する、といった文で「Null参照例外」と訳さない
- 長く連なる単語では翻訳した漢字とカタカナが交互に並ぶようにすると少し見やすい

## 翻訳調・直訳構文の回避

英語の原文や思考をそのまま直訳したような、不自然な言い回しや構文を避ける。

- **「〜できない理由」構文を避ける**
  - 英語の "Reasons why ... cannot be done" の直訳（例: 「アルファ閾値を作れない理由」「公開できない理由」）を避け、「〜の生成失敗エラー」「〜の検証エラー」「〜の失敗事由」のように、事象や役割を表す名詞表現にする。
- **過去形・擬人化を避け、客観的な現在形・条件記述にする**
  - 状態やエラー原因の説明で「〜だった」「〜した」（例: 「値がNaNだった」「フレームを公開しようとした」）と書かず、「〜である場合」「〜のとき」「〜が指定された場合」と客観的な条件・状態で書く。
  - コードや型を擬人化して「関数が〜を拒否する」「型が〜を持ち込まない」とするのではなく、「〜の場合はエラーを返す」「〜の混入を防ぐ」のように主客のねじれを正す。
- **"semantics" を文脈なく「意味」と直訳しない**
  - "semantics" は無批判に「意味」と訳すと哲学的・観念的になりやすい。文脈に応じて「属性」「パラメータ定義」「解釈」「マッピング」「仕様」など具体的な言葉に言い換える。

## 修正例

Renderer の Update Pipeline では、各 Frame ごとに Scene 内の Object State を Collect して、Visibility Check の Result を Based に Render Target への Draw Call を Dispatch します。このとき Material ごとの Shader Variant を Runtime で Resolve すると Performance Overhead が Increase するため、可能であれば Build Time に Precompile して Cache しておくことを Recommend します。
↓
レンダラの更新用パイプラインではフレームごとにシーン内のオブジェクトの状態を収集し、可視性チェックの結果を元にレンダーターゲットへのドローコールを発行します。実行時にシェーダーバリアントのコンパイルが発生すると処理負荷が増えるのでビルド時にコンパイルしてキャッシュする設定がおすすめです。

Texture Atlas を Generate する Process では、各 Material が Reference している BaseColor Texture を Collect したあと、Packing Algorithm を Apply して Atlas 上の Region を Allocate します。その後、Mesh の UV Coordinate を Atlas Space に Remap し、Material Parameter についても Unified Shader から Access できるよう Buffer に Serialize します。
↓
アトラステクスチャの生成プロセスでは各マテリアルが参照するベースカラーテクスチャを収集後、パックしてアトラス上の領域を割り当てます。その後メッシュのUVをアトラス空間に合わせて変形し、マテリアルパラメータは統一シェーダからアクセスできるようにバッファにセットします。

GPU Particle System を Implement する場合、Particle State を Storage Buffer に Store して、Compute Shader の Dispatch ごとに Position と Velocity を Update します。ただし Particle Count が Large になると Memory Bandwidth が Bottleneck になるため、Data Layout を Optimize したり、不要な Attribute を Remove したりして、Buffer Access の Efficiency を Improve する必要があります。
↓
GPUパーティクルを実装する場合、パーティクルの状態はStorage Bufferに保持してコンピュートシェーダの実行ごとに位置、加速度を更新します。ただ、パーティクルが多すぎるとメモリ帯域律速になるため、この場合はレイアウトの工夫や不要なアトリビュートの削除などによるバッファアクセス最適化が必要です。

## 具体事例

- `Web`は英単語の方がいい
- `Readback`は`読み戻し`で翻訳
- `パディング`はカタカナ
- `Resource`は`リソース`（CG/GPU関連で「資源」と無理に訳さない）
- `Directional Light`は`平行光源`または`ディレクショナルライト`（「方向光」などの造語を避ける）
- `Store`は`ストア`（データ構造を「保管庫」と訳さない）
- `Command Submission`は`GPUへのコマンド提出（Submit）`（単に「提出」としない）

## 新規作成ドキュメントについて

人間と共同で新規にドキュメントを作成する場合、初期段階ではできるだけ内容を小さくまとめること。
より抽象的、コンパクトなところから始めて徐々に内容を膨らませていくべきである
