# Rustを書くときのルールや推奨方針

## Rust基本指針

コンパイル時に保証可能な設計上の制約は、コメント・命名規則・実行時チェックではなく、可能な限りRustの型システム・所有権・可視性によって表現する。
ただし、型レベル設計の複雑さが、それによって排除されるバグの重大性を上回る場合はランタイム表現を選択する。
ランタイム表現を選択する場合、設計理由としてのADRコメントを書くことが望ましい。

- **不正な状態を型で表現できないようにする。** 状態依存フィールドはenum、意味の異なるプリミティブ型はNewtypeを使う。
- **所有権・borrow・`&mut`をAPIの意味として使う。** `clone`、`Arc`、`Mutex`で所有権問題を安易に回避しない。
  - 特に安易なcloneの連発はパフォーマンス上の問題を生みやすいため、記述時、レビュー時の双方で厳しくチェックする
- **公開型の不変条件はconstructorとprivate fieldで保証する。**
- **閉じた多態性にはenum、開いた多態性にはtraitを使う。**
  - バリアント集合がライブラリ内部で閉じている概念にはトレイトや継承的設計よりenumを優先する。
  - トレイトは「その型が何であるか」より「何ができるか」を表現する。独立して利用可能な能力は小さなトレイトへ分割する。
- **失敗はResult、正常な欠損はOptionとして表現する。** panicや番兵値で通常の制御フローを表現しない。
- **リソース寿命や後片付けはRAIIへ寄せる。** 後片付けを呼び出し側の規約に依存させず、可能な限り所有オブジェクトのDropへ結び付ける。
- **可変性、可視性、借用範囲を必要最小限にする。**
- **型変換はFrom / TryFrom等の標準トレイトへ集約する。**
- **重大な状態遷移制約にはtypestateを検討する。** 主に公開APIや重要なリソースのライフサイクルについて
  - 使いすぎて型が爆発しないよう注意
- コレクションの変換・絞り込み・集約では主にIteratorを優先する。ただし、過剰に複雑になる場合はループでよい。
- pubをデフォルトにしない。公開範囲は必要最小限とし、クレート内部APIにはpub(crate)等を使用する。

## コメントについて

コメントの共通方針は[コード記述共通ルール](../../../apm_modules/halby24/agent-common-package/.apm/skills/code-writing/SKILL.md#コメントについて)に従う。
公開APIにはrustdocのdocコメント（`///`・`//!`）を書く。非公開の項目には、名前や型から読み取れない情報がある場合に書く。

- 最初の段落は役割や処理を短く要約する。rustdocの一覧にも表示されるため、詳細とは空行で分ける。
- 型やシグネチャの言い換えを避け、単位、値域、`None`の意味、状態変化など、利用時に必要な情報を補う。
- 見出しは必要なものだけ使う。引数や戻り値の説明は本文を基本とし、項目が多い場合に見出しや箇条書きで整理する。
- 同じ説明を繰り返さず、関連項目は ``[`Scene::tick`]`` 形式のリンクで参照する。

### モジュールスコープ

クレートルートや公開モジュールには、`//!`で役割と利用の入口を書く。
内部モジュールは、責務の境界や処理の流れを説明する必要がある場合に書く。短いファイルすべてに定型文を付ける必要はない。

- **クレートルートでの `pub mod` とモジュール内 `//!` の重複防止**:
  - `lib.rs` 等の `pub mod foo;` に付けるコメントは、簡潔な名詞句や短い要約にとどめる。
  - モジュール内部の `//!` でその詳細な役割や利用の入口を説明する。
  - 両方に同じ内容の文を書くと、rustdoc生成時のモジュール一覧で同じ説明が二重に連結されて表示されるため避ける。

```rust
//! シーンと、その内部に配置するオブジェクト（アバター、カメラ、…）の状態管理
//!
//! [`Scene::tick`] が毎フレームの更新窓口となる。
```

### 型・フィールド・バリアント

- 型が表す概念と、利用者に保証する性質を書く。不変条件の説明が必要なら`# 不変条件`にまとめる。
- フィールドやバリアントには、値の意味、単位、状態の違いなどを書く。非公開項目で自明な説明は省く。
- **エラー型（enum）の表現**:
  - 英語の直訳調（「〜を作れない理由」「〜できない理由」）を避け、「〜の生成失敗エラー」「〜の検証エラー」「〜のエラー」のように型としての役割を表す表現にする。
  - バリアントの説明は「〜だった」のような過去形ではなく、「〜である場合」「〜のとき」と現在形・条件記述にする。
- 初期値については、どのコンストラクタや`Default`が設定する値かを明示する。利用者向けの説明は生成側にまとめ、内部の初期化理由は通常コメントに書く。
- 内部のデータ構造を選んだ理由などは通常コメントに書く。docコメントには利用判断に必要な説明を載せる。

### トレイト

利用者向けの役割に加え、実装者が守る条件を書く。メソッド間の整合性、関連型の意味、許容する失敗などを必要に応じて説明する。
共通の説明はトレイト側にまとめる。実装側はrustdocによる説明の継承を利用し、固有の挙動がある場合だけ補足する。
`unsafe trait`には、実装者が保証する安全条件を`# Safety`に書く。

### 関数・メソッド

実際のシグネチャと挙動に沿って説明する。呼び出し順序、副作用、失敗時の状態や部分的な処理の有無も、利用者の判断に必要なら書く。

- `# Errors`: `Err`を返す条件を書く。「〜を明示的に拒否する」のような擬人化・直訳調を避け、「〜の場合にエラーを返す（または返す条件）」という客観的な結果記述にする。
- `# Panics`: 利用者が遭遇し得るパニックの条件を書く。`Result`を返す関数でも必要になる場合がある。
- `# Safety`: `unsafe fn`の呼び出し側が守る安全条件を書く。内部で`unsafe`を使うだけの安全な関数には付けない。

各見出しは排他的ではなく、該当するものを併記する。

以下は`Scene`のメソッド定義部分の例（実装は省略）。

```rust
/// ポーズを更新して描画命令を発行し、このフレームの統計を返す。
///
/// `delta_time`は前回の更新からの経過時間をミリ秒で指定する。
/// 有限かつ0以上1000未満の値を受け付ける。
/// 戻り値の[`FrameStat`]には描画したアバター数を含む。
///
/// # Errors
///
/// `delta_time`が範囲外、`NaN`、または無限大の場合に返す。
/// この場合、シーンの状態は変更せず、描画命令も発行しない。
pub fn tick(&mut self, delta_time: f32) -> Result<FrameStat, TickError> {
    // 実装省略
}
```

### 実装の根拠

- `unsafe`ブロックや`unsafe impl`の直前には、必要な安全条件がその場所で満たされる根拠を`// SAFETY:`に続けて日本語で書く。「高速化のため」などの採用理由では代用しない。
- `unwrap`・`expect`には、失敗しない前提とその成立根拠を残す。コードや`expect`のメッセージで明確なら、同じコメントを重ねない。パニックし得るAPIでは、その条件を`# Panics`に書く。
- 非自明な`clone`には、複製が必要な理由やコスト上の判断を書く。自明な複製に定型のADRコメントを付ける必要はない。

### 使用例と検証

- 利用手順や所有権の扱いが分かりにくいAPIには`# Examples`を付ける。単に呼ぶだけの例を量産せず、関連項目の例へのリンクも利用する。
- ソース内のdocコメントに載せるRustコードは、原則としてドキュメントテストでコンパイル・実行できる形にする。失敗する操作の例では`?`によるエラー処理を示す。
- 実機や外部環境が必要な例には`no_run`を使い、コンパイル検証を残す。`ignore`は検証を省く必要がある場合に限り、理由を添える。
- docコメントを変更したら、対象クレートの`cargo doc --no-deps`でリンクや警告を確認し、使用例を変更した場合は`cargo test --doc`で検証する。必要な機能フラグは対象クレートの手順に従う。

書式の詳細は[rustdocの執筆指針](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)、安全条件などの説明は[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/documentation.html#c-failure)を参照する。
