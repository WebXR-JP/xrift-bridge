# プロトコル

初期の認証、通信形式、二種類の配送、流れ制御、制限、エラーの扱いを決める

## 接続前検証

- WebSocket の昇格前に以下を確認する。
  - 接続元IPがループバックであること。
  - ホスト、ポート、パスが設定した接続先と一致すること。
  - `Origin` を完全一致で許可する。本番は `https://app.xrift.net`、開発は明示的な開発モードのみであり、許可する `Origin` は設定に列挙して完全一致で判定する（例: `http://localhost:5173`）。
  - 欠落した `Origin`、`null`、ワイルドカード、接尾辞一致は拒否する。
- WebSocket の安全性を CORS ヘッダに依存させない。

## ペアリングと認証

1. 利用者がローカルブリッジの CLI から明示的にペアリングを開始する。
2. 暗号学的乱数による 128 ビット以上の秘密値を生成する。120 秒有効、一度だけ使用可能、許可した `Origin` に紐付ける。
3. ワールド画面で秘密値を入力して接続する。
4. 最初のアプリケーションメッセージで認証する。認証前はデータとローカル情報を送受信しない。
5. 成功した WebSocket 接続だけを認可する。切断で認可は失効し、再接続には再ペアリングが必要である。

- 秘密値を URL、クエリ、Cookie、ログ、ブラウザの永続ストレージに入れない。
- 認証待ちのタイムアウト、試行回数制限、接続数制限を設ける。
- ローカル管理は接続一覧（接続ID・Origin・認証状態）と接続ID指定の切断を提供する。指定接続だけを切断し待ち受けと他接続は維持する。全体停止とは区別する。
- Origin は「そのワールド」の識別に使えない。同一文書・同一スクリプト実行基盤のため、XRift ホストと同じ基盤内のコードから秘密値や通信を隔離できない。ワールドID、表示名、SDK 内部変数は認証境界にならない。

## 通信形式

- JSON メッセージとする。バイナリ形式は計測後である。
- 接続セッション識別子、ストリーム識別子、種別、ストリーム内連番を持つ。
- 順序保証はストリーム内である。異なるストリーム間の全体順序は保証しない。
- コマンド処理結果は要求IDへの明示応答とする。切断時の未完了コマンドは結果不明とする。

## 二種類の配送

- `reliable`
  - コマンド、テキスト、AI 逐次出力、欠落不可のセンサー列に使う。ストリーム内の順序を保持する。満杯時は待機または明示エラーとする。
- `latest`
  - 独立した状態のスナップショットに使う。ストリームごとに未送信の古い値を最新値で置換できる。欠番を許容する。配送と遅延の上限を保証しない。
- `latest` の置換の考え方は今入れるが、本物の非信頼データグラムは後回しである。WebSocket 上での最新値優先の配送である。
- 高頻度センサーのすべてを `latest` にはしない。位置の絶対値は適するが、差分、積分用サンプル、イベントは欠落で意味が壊れ得る。既定は `reliable` とし、`latest` は明示選択である。

## 流れ制御と待ち行列

- 送信側、受信側の両方に有限の受信箱が必要。
- 送受信の待ち行列を有限に抑える。件数、バイト数、ストリーム数の直接制限に限らず、
  受付時に検査した要素上限から導く有限 bound でもよい。
  各待ち行列が独立した3種類の上限値を必ず持つ方式には限定しない。
- `reliable` には受信側容量を反映するクレジット・ウィンドウ制御を入れる。
  - クレジットは接続単位であり、全 `reliable` ストリームで共通である。
  - `reliable` フレームを実際に送出したときに1件消費する。ローカル待機への追加では消費しない。
  - `latest`・認証・制御フレームは消費しない。
  - 回復の原因は受信側で予約していた容量の解放である。応答受信やコマンド成功そのものではない。
  - ブリッジからクライアントへの credit が制御するのはクライアントからブリッジへの受付容量である。クライアントの未処理応答量ではない。
  - `credit` 通知は処理完了の応答とは別物である。
- credit 通知と送信の交差で過剰送信を防ぐため、残数ではなく累積付与件数を通知する。
  - 残数解釈の旧wireとは互換性がなく、版を上げる要件である（版番号の正本は実装の `PROTOCOL_VERSION` とする）。
    旧wireの `window` は残数の上書き通知であり、累積件数の `limit` とは解釈が異なる。
  - `auth_ok.window` は初期付与件数である。
  - `credit.limit` はこの接続で送信を許可した累積件数である。クライアントの送信可能残数 = `limit` − 累積送信件数である。
  - `limit` は `auth_ok.window` を初期値として接続内で単調非減少に通知する。付与済みの送信権は撤回しない。
    受信側は、現在の累積付与上限より小さい同一セッションの通知を無視し、会計を変更しない。この無視ではエラー通知・切断をしない。
    同値の再通知は追加付与にならない。これは送信側の古い会計値の誤再通知による進行停止を防ぐためであり、
    輸送順序逆転への対処ではない。
  - セッション不一致の credit は会計・エラー応答のいずれにも適用せず無視する。
  - 切断・再認証で会計をリセットする。
- サーバは接続単位で次の会計不変条件を保つ。C を `reliable` 受付の件数容量（`maxReliableQueueMessages` と同一で、未送信・送信中の応答保持を含む）、G を累積付与件数、R をクレジット消費済みの受信件数、U を受信済みで容量未解放の件数とし、常に `(G − R) + U <= C` を保つ。追加付与可能量は `C − U − (G − R)` である。
  - 受信時は残る権利を占有量へ移し、容量解放時に追加付与する。
  - 未送信応答と送信中応答を容量に含め、ブリッジ内部の送出完了通知で枠と保持バイトを解放する。完了通知の失敗は切断とする。
  - 業務エラーで拒否した要求の枠は、可能な限り解放する。解放できない場合のみ切断し、枠を永久に失わせない。
    - 連番・ストリーム数超過の拒否は枠を解放して継続する。
    - 付与超過はクレジット消費前に業務処理せず明示拒否して切断する。
    - 応答保持の容量超過は消費済み予約を解放したうえで切断する。
  - 初期付与が件数容量を超える設定は、起動時設定検証（`resolveLimits`）で拒否する。
- クライアントは累積付与上限と累積送信件数で会計し、応答の受信だけでは回復させない。
- クライアントの reliable 送信待機は最大 N 件（`maxPendingReliable`）であり、
  各メッセージは受付前に最大 M UTF-8 bytes（`maxMessageBytes`、JSON 全体を計測）の検査を受ける。
  待機データは最大 N×M bytes に収まる。待機総バイトの独立上限は設けない。`latest` の送信も同じ1件検査を受ける。
  超過はローカルの明示エラーにし、待機枠・クレジット・連番を消費せず、切断しない。
- この待機 bound は待機データ（N×M）の範囲であり、JS ヒープ全体、シリアライズの一時領域、
  送信済み WebSocket バッファ、未応答管理、ストリーム対応表まで制限しない。
  クライアントの送信上限とブリッジの受信上限は別設定であり、一致の交渉はしない。
- 件数 credit は「その件数なら任意サイズの要求が必ず成功する保証」ではない。バイト上限（`maxMessageBytes`・`maxReliableQueueBytes`）は独立した硬い制限である。`maxMessageBytes` 超過は `ws` の `maxPayload` 委譲で close 1009 により通知する。`maxReliableQueueBytes` 超過は `QUEUE_FULL` の明示エラーと 1011 切断になる。ブリッジ内部の送出完了通知はクライアントのアプリ処理完了を保証せず、保証するのはブリッジ内の受付・応答保持容量のみである。
- `latest` は各ストリームの未送信最新値と送達中の量を制限する。受信側も最新値の受信箱として保持してよい。
- 共通の配送順決定で制御メッセージを優先し、AI の大量出力とセンサーが互いを無期限に阻害しないよう公平に送る。
- 最大メッセージ長を制限する。容量の単位は UTF-8 にシリアライズした JSON メッセージのバイト数とする。
- 単一メッセージの受信上限（`maxMessageBytes`／`ws` の `maxPayload`）の超過は close 1009 による通知でよい。`maxReliableQueueBytes` の超過は別で `QUEUE_FULL` 明示エラーと 1011 切断である。
- 切断時は送受信の待ち行列と未完了の待機を破棄して通知する。
- 送信済みの古い値は WebSocket から取り消せない。`latest` でも TCP 内に入ったデータの停滞は残る。
- 待ち行列容量等の初期数値は計測用の有限・設定可能な暫定値とし、検証実施前に [検証 v0](verification-v0.md) の試作条件に記載して測定結果から合意する（合意待ち）。

## 制限とエラーの扱い

- エラーは待機または明示エラーで返す。
- 切断時の未完了分は破棄して通知する。
