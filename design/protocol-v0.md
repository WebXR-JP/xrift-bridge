# プロトコル v0

この文書は初期の認証、通信形式、二種類の配送、流れ制御、制限、エラーの扱いを決める文書である。輸送手段と接続先、状態遷移の正本は [ブリッジ接続 v0](bridge-v0.md) とし、証拠の集め方は [検証 v0](verification-v0.md) とする。ここでは要約の複製を作らない。

## 状態

- 確定事項: この文書に「確定」と書いた判断は変更しない。
- 検証待ち: [検証 v0](verification-v0.md) の観測で確認する事項である。
- 合意待ち: 利用者との合意がまだの事項である。本文では末尾の区分表に集約し、都度の記述では `検証待ち` `合意待ち` と添える。

## 接続前検証

確定事項である。

- WebSocket の昇格前に以下を確認する。
  - 接続元IPがループバックであること。
  - ホスト、ポート、パスが設定した接続先と一致すること。任意のDNS名を受け付けない。
  - `Origin` を完全一致で許可する。本番は `https://app.xrift.net`、開発は明示的な開発モードのみであり、許可する `Origin` は設定に列挙して完全一致で判定する（例: `http://localhost:5173`）。
  - 欠落した `Origin`、`null`、ワイルドカード、接尾辞一致は拒否する。
- WebSocket の安全性を CORS ヘッダに依存させない。

## ペアリングと認証

確定事項である。接続の状態遷移は [ブリッジ接続 v0](bridge-v0.md) を参照する。

1. 利用者がローカルブリッジの CLI から明示的にペアリングを開始する。
2. 暗号学的乱数による 128 ビット以上の秘密値を生成する。120 秒有効、一度だけ使用可能、許可した `Origin` に紐付ける。
3. ワールド画面で秘密値を入力して接続する。
4. 最初のアプリケーションメッセージで認証する。認証前は業務データとローカル情報を送受信しない。
5. 成功した WebSocket 接続だけを認可する。切断で認可は失効し、再接続には再ペアリングが必要である。

付随条件は確定事項である。

- 秘密値を URL、クエリ、Cookie、ログ、ブラウザの永続ストレージに入れない。
- 認証待ちのタイムアウト、試行回数制限、接続数制限を設ける。
- ローカル側から接続確認と切断ができる。
- Origin は「そのワールド」の識別に使えない。同一文書・同一スクリプト実行基盤のため、XRift ホストと同じ基盤内のコードから秘密値や通信を隔離できない。ワールドID、表示名、SDK 内部変数は認証境界にならない。

## 通信形式

確定事項である。

- v0 は JSON メッセージとする。バイナリ形式は計測後である（検証待ち）。
- 接続セッション識別子、ストリーム識別子、種別、ストリーム内連番を持つ。
- 順序保証はストリーム内である。異なるストリーム間の全体順序は保証しない。
- 切断後の再送、セッション復元、厳密な一回限りの配送は提供しない。
- ローカルの受理、相手の受信、相手の処理完了を区別する。
- コマンド処理結果は要求IDへの明示応答とする。切断時の未完了コマンドは結果不明とし、失敗断定や自動再実行をしない。
- 上位層に WebSocket オブジェクトを公開しない。
- 具体的な字段名・型・必須/任意は `packages/bridge-protocol` の共有定義を正本とする。

## 二種類の配送

確定事項である。欠落許容の合意は合意待ちである。

- `reliable`: コマンド、テキスト、AI 逐次出力、欠落不可のセンサー列に使う。ストリーム内の順序を保持する。満杯時は待機または明示エラーとし、黙って捨てない。
- `latest`: 独立した状態のスナップショットに使う。ストリームごとに未送信の古い値を最新値で置換できる。欠番を許容する。配送と遅延の上限を保証しない。
- `latest` の置換の考え方は今入れるが、本物の非信頼データグラムは後回しである。WebSocket 上での最新値優先の配送であり「データグラム対応」とは呼ばない。
- 高頻度センサーのすべてを `latest` にはしない。位置の絶対値は適するが、差分、積分用サンプル、イベントは欠落で意味が壊れ得る。既定は `reliable` とし、`latest` は明示選択である。

## 流れ制御と待ち行列

確定事項である。容量の初期数値は計測用の暫定値であり合意待ちである。

- 有限の待ち行列は送受信の両端で必要である。
- 送受信の待ち行列をバイト数、件数、ストリーム数で制限する。
- `reliable` には受信側容量を反映するクレジット・ウィンドウ制御を入れる。処理完了の応答とは別物である。
- `latest` は各ストリームの未送信最新値と送達中の量を制限する。受信側も最新値の受信箱として保持してよい。
- 共通の配送順決定で制御メッセージを優先し、AI の大量出力とセンサーが互いを無期限に阻害しないよう公平に送る。配送順決定の具体則は合意待ちである。
- 最大メッセージ長を制限し、AI 出力を無制限の巨大フレームにしない。
- 切断時は送受信の待ち行列と未完了の待機を破棄して通知する。
- 送信済みの古い値は WebSocket から取り消せない。`latest` でも TCP 内に入ったデータの停滞は残る。期限や厳密な鮮度保証は未確定とし、計測用のタイムスタンプを性能保証に読み替えない（検証待ち）。
- 待ち行列容量等の初期数値は計測用の有限・設定可能な暫定値とし、検証実施前に [検証 v0](verification-v0.md) の試作条件に記載して測定結果から合意する（合意待ち）。

## 制限とエラーの扱い

確定事項である。

- 秘密値の扱い、認証待ちのタイムアウト、試行回数、接続数の制限はペアリングの節に従う。
- 対象範囲と包括許可にしない扱いは [ブリッジ接続 v0](bridge-v0.md) の対象範囲に従う。
- エラーは黙って捨てず、待機または明示エラーで返す。切断時の未完了分は破棄して通知する。
