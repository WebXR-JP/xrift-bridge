# 比較コード承認の実機手順書

人間が実機で比較コード方式の接続承認を通し、結果を記録するための手順書である。検証計画の正本は[ブリッジ検証計画](bridge.md)のままとし、本書は実施手順と記録用紙に限定する。設計判断は[ブリッジ接続](../../design/bridge.md)と[プロトコル](../../design/protocol.md)を正本とし、ここでは繰り返さない。形状・符号は `packages/bridge-protocol/src/messages.ts`、制限値の正本は `apps/bridge/src/config.ts` の `DEFAULT_LIMITS` とする。

## 目的と前提

受付の開閉から比較コードの目視照合、承認、認可後の到達性確認、失効と再接続までの一連の流れを人間が実機で確認する。対象は Google Chrome（必須）、XRift（開発または本番）、ブリッジ CLI、診断ワールドである。

以下は自動試験で代替できないため人間が行う。実施前に 0.3 の実装を再アップロードすること（記録上の最新アップロードは 0.2 時点の version 1 であり、0.3 でのサーバ側審査・実ホスト確認は未了である）。

- ローカル網アクセスの初回許可・拒否・取消後の挙動は利用者の操作とブラウザ表示に依存する。
- XRift の審査通過と宣言内容の一致は実経路でのみ確認できる。
- 実測のコンテンツセキュリティポリシーと `Origin`・SecureContext・フレーム構造は実機の値を使う。
- 両画面の比較コード一致は人間の目視照合そのものが要件である（コード一致だけでの自動認可はしない）。

## 準備

### ブリッジの起動

手順は `apps/bridge/README.md` に従う。

```bash
vp run bridge#build
node apps/bridge/dist/index.mjs --port 3100
# 開発時（明示的開発モードでのみ追加 Origin を許可）
node apps/bridge/dist/index.mjs --dev --origin http://localhost:5173
```

- 本番経路の既定許可 `Origin` は `https://app.xrift.net` であり、正本は `apps/bridge/src/verify.ts` の `PRODUCTION_ORIGIN` とする。
- 開発時は `--dev` と `--origin http://localhost:5173` を付け、`accept open` の前に許可 `Origin` を確認する。`--origin` は `--dev` なしでは起動失敗する。
- 待ち受けは `127.0.0.1` への明示 bind であり、正規接続先は `ws://127.0.0.1:3100/v1` である。ポート競合時は探索せず失敗する。
- 対話命令の一覧は起動時の表示と `--help` の出力が正本である（`accept open`・`accept close`・`pending`・`approve <requestId> <code>`・`reject <requestId>`・`status`・`connections`・`disconnect <connectionId>`・`quit`）。

### 診断ワールドの起動

手順は `apps/diagnostic-world/README.md` に従う。

```bash
# 開発時（http://localhost:5173 固定。競合時は退避しない）
vp run diagnostic-world#dev
```

- 開発パネルは `http://localhost:5173` を開く。本番は XRift 上の診断ワールド（in-world 操作盤）を開く。
- ルートの `dev` は website を起動するため使わない。
- 操作盤のボタンは「接続開始（比較コード表示）」「echo 往復」「ping」「取消／切断」である。承認操作はブリッジ側 CLI からのみ行い、ワールド側からの承認は受け付けない。

### 記録すべき環境情報

開始前に以下を記録用紙へ転記する。

- 実行ビルドの識別子（診断盤の `build` 表示：版・コミット・ビルド時刻）。
- プロトコル版 `0.3.0`（正本は `packages/bridge-protocol/src/messages.ts` の `PROTOCOL_VERSION`）。
- OS と Chrome の正確な版。
- ブリッジの実効制限値（正本は `apps/bridge/src/config.ts`。上書き時は `BridgeOptions.limits` の実効値を残す）。
- 許可 `Origin` の一覧と使用した接続先。
- 診断盤の環境表示（`origin`・SecureContext・top-level／embedded）。

## 手順

各項は操作と期待結果の対である。比較コードは文字列のまま扱い、数値化しない（先頭ゼロ保持。例 `000123`）。表示は `123 456` のように3桁区切りである。

1. CLI で `accept open` を入力する。`acceptance state=open` と終了時刻・残時間が表示される。起動時は閉じていること。
2. 診断盤で「接続開始」を押す。盤の進行が「承認待ち」になり、比較コードが区切り表示される。
3. CLI で `pending` を入力する。要求 ID・`Origin`・区切り付きコード・残時間が表示される。両画面のコードが一致することを目視で照合する。一致の記録は「一致した事実」のみとし、コード本文は残さない。
4. CLI で `approve <requestId> <6桁コード>` を入力する（コードは区切りなし6文字の文字列）。`approved <requestId> connection=<connectionId>` が表示され、盤が「認証済み」へ遷移する。ワールド側へ `auth_ok` が届いた接続だけが認可される。
5. 盤で「echo 往復」を押す。表示が「一致」になる（診断が採番した操作番号・バイト数・往復時間のみ残り、wire の連番は表示しない）。
6. 盤で「ping」を押す。表示が「pong」になる（`data` 上の診断 payload `{op: "ping", id}` に対する `{op: "pong", id}` の応答。yamux 監視 Ping とは別物）。
7. 誤コードの確認。別の承認待ち要求でわざと1桁変えたコードを `approve` する。`approve 失敗: CODE_MISMATCH <requestId>` となり、保留は残って接続も維持される。正しいコードで承認し直す。
8. `reject` の確認。新しい要求を作り、CLI で `reject <requestId>` を入力する。`rejected <requestId>` が表示され、対象の接続が終了する。
9. 取消の確認。新しい要求を作り、承認前に盤で「取消」を押す。承認待ち表示が消え、CLI の `pending` からも消える。
10. 受付クローズの確認。CLI で `accept close` を入力する。`acceptance state=closed` となり、開始待ち・承認待ちがすべて終了する。認可済み接続は維持され、echo が通ることを確認する。
11. 承認前の業務操作の拒否を確認する。未認可の接続から `create_session`・`data` を送ると終端エラー（`NOT_AUTHORIZED`）で終了し、逆方向メッセージも受け付けない。診断盤では承認前に echo／ping ボタンが押せないことで代用してよい。
12. 切断後の再接続を確認する。盤で「切断」し、再び「接続開始」を押す。新しい要求 ID と新しいコードが発行され、再承認が必要であることを確認する。承認後に echo が通る。
13. 受付を閉じたまま接続開始を試みる。要求は upgrade 時に拒否され、保留・通知しない。`pending` は空のままである。
14. 期限切れを確認する。承認せずに放置し、保留が失効して接続が終了すること（`PAIRING_EXPIRED`）を確認する。以降は新規に接続開始する。
15. CLI で `status` を入力する。受付状態・終了時刻・接続数・認可数・保留数・成功／失敗数・理由別拒否集計を確認し、記録用紙へ転記する。

期限・上限・レートの期待値（開始10秒・承認120秒・受付120秒・全8／未認可2／保留2・レート等）は `apps/bridge/src/config.ts` を正本とし、ここでは再掲しない。

## 証拠の取り扱い

- 比較コードは両画面への表示と照合にだけ使う。ログ・URL・クエリ・永続保存・証拠に含めない。
- 診断結果 JSON（`toResultJson`）は比較コード本文と業務 payload を含まない設計であり、`pairingShown` に表示した事実だけを残す。保存・コピー時はこの JSON を使う。
- 比較コードを含む画面の撮影は要求終了後の最小限に留める。撮影した場合はコードが読めない形で保管するか、照合の事実だけを記録して画像を破棄する。
- 通常の診断ログは標準エラーへの JSON であり、比較コードは標準出力の `pending` 表示にだけ出す。

## 判定と分岐

成功・失敗の判定基準と対応表の作り方は[ブリッジ検証計画](bridge.md)の実行条件・判定後の分岐を正本とする。ここでは実機での切り分け順のみ記す。

- 接続自体が届かない場合：接続先（数値 IP・ポート・パス `/v1`）・許可 `Origin`・待ち受けポート・CSP・LNA 許可の順に確認する。
- 要求が保留にならない場合：受付が開いているか、開始メッセージが接続につき1回か、レート・上限超過で `status` に集計されていないかを確認する。
- 承認が通らない場合：要求 ID とコードの組・期限・接続の生存・受付状態を確認する。符号（`CODE_MISMATCH`・`PAIRING_EXPIRED`・`ACCEPTANCE_CLOSED`・`NOT_PENDING`・`CONNECTION_GONE`）で切り分ける。
- 認可後に業務が通らない場合：認可状態と接続 ID・Session の対応を確認する。認可前の操作は拒否が正しい。
- ブラウザの安全機能を無効化した成功は合格にしない。
- XRift の審査不通過は正式な許可可否を確認し、検出されない API への置換で迂回しない。
- 切り分けがつかない場合は `status` 出力・診断結果 JSON・環境情報を添えて設計へ再相談する。

## 未確認として残る範囲

- 待ち受けが LAN 側に露出していないことの確認は別途行う（本書の手順では扱わない）。
- Safari を含む Chrome 以外での接続は約束しない。対応表は観測結果で作る。
- 配送と負荷の試作条件・計測項目は[ブリッジ検証計画](bridge.md)を正本とし、本書では扱わない。
